# Factory 2.1.0 — release record

2.1.0 is the release after 2.0.0 ([v2-release.md](v2-release.md)). It carries PR #4: the
fixes found when 2.0.0 was validated with live agent hosts and then used for a production
run, recorded in
[handoff/2026-09-27-production-validation.md](handoff/2026-09-27-production-validation.md).
What changed is in [CHANGELOG.md](../CHANGELOG.md) under 2.1.0.

It is a minor version: it adds the live build (`scripts/golden/live.py`, `test_live_loop`),
two archetypes (`drop-merge`, `arena-dodge`) and two blocking design-consistency rules
(`concept_mechanics_carried`, `design_adds_no_foreign_mechanic`), and fixes the sdk step and
the developer brief. No default a 2.0.0 installation relies on changed, no schema changed,
and the `new-game` workflow definition is unchanged.

## Review of PR #4

The 12 commits of `fix/live-agent-reproducibility` (from `5b74e30`) were reviewed against
`main`: design selection and the concept rules, the sdk placement fixes, the brief, the
golden warm-up, the live build and its sandbox seam, the tests changed or removed, the
committed handoff tarball (run-store JSON and logs only: no game source, no credentials),
and the CHANGELOG. One defect was found and fixed on the branch before merging:

- **A live run started without a run budget** (`50cb49d`). The production validation says
  every run ran under `develop.budget {max_sessions: 6, max_cost: 120}`, but `live.py
  config` wrote none; it had been added by hand. The budget is snapshotted when a run starts
  and cannot be added later. `build_live_config` now writes it and records it in
  `live-agents.json`; the regression test fails on the unfixed code.

Removed live tests (`LiveDeveloperAndReviewer`) and the changed `LiveReviewer` assertion are
not a weakening: the convergence they asserted moved to `test_live_loop`, which a real build
can satisfy (CHANGELOG 2.1.0, *Fixed*).

Merged as `931cb04` (a merge commit; its tree is identical to the reviewed `50cb49d`).

## 2.1.1 (2026-09-28)

A patch release: one false positive in the develop step, found by the production run started
on 2.1.0 (`new-game-20260927-155337-3c1781`). Its developer replaced the template's scaffold
scene with the game's own first scene, as the brief asks, and named that class `BootScene`
(`src/scenes/boot-scene.ts`); the conformance check matched the word `BootScene` in
`src/main.ts` and refused all three attempts, so the run failed at develop with a conformant
build (the other six develop checks green each time). The check now judges the module an
import resolves to: game source importing the template's `src/game/boot-scene.ts` - directly,
dynamically or through another module - is refused; a game-owned `BootScene` is not. The
rule itself is unchanged. CHANGELOG 2.1.1 has the details and the regression tests.

Pins as for 2.1.0; `VERSION` 2.1.1. The template contract lists one more source path
(`src/game/boot-scene.ts`), present in the pinned template; `CONTRACT_VERSION` is unchanged.

The validation ladder - the same as 2.1.0's - is run on the release commit before tagging, and
its result is recorded in the `v2.1.1` tag annotation. The failed production run is resumed on
2.1.1, not restarted: its steps up to develop visit 1 ran on 2.1.0, and everything from the
resumed develop step runs on 2.1.1 (the run's handoff records which step ran on which
version).
