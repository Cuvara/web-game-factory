# Factory 2.3.0 — release record

2.3.0 is the release after 2.2.0 ([v2.2-release.md](v2.2-release.md)) and carries three
merges:

| PR | What |
|---|---|
| #10 | A Linux acceptance runner. The release gate `WGF_GOLDEN=1 bin/wgf test-core --strict` could not execute on the Windows host the recent work was developed on, on any branch including `main`; both goldens died in `setUpClass` on `pnpm`. The harness was not patched — a POSIX runner was added |
| #9 | The Three.js developer foundation: three 3D craft playbooks, `architecture.physics` decided at G3, engine notes in the develop brief, adapter binding 1.3.0 |
| this | **Phaser as a second 2D engine** — `engine.type` accepts `phaserjs`, the pinned template ships a Phaser binding, and a Phaser title gets its own craft playbook and skill, adapter binding 1.4.0 |

PixiJS remains the 2D default and is unchanged. What changed, and what an upgrade will show,
is in [CHANGELOG.md](../CHANGELOG.md) under 2.3.0.

This page records the Phaser half; the 3D half is in [3d-benchmark.md](3d-benchmark.md).

## Why the contract is major

`CONTRACT_VERSION` follows acceptance, not size. `packages/phaser-framework/` and
`src/rendering/phaserjs/` follow from the new engine id by the template's naming convention
and are **required** entries, so `init` now refuses a repository generated from a template
that predates them. By the rule in `wgflib/template_contract.py` that is a major. It is the
whole breaking surface: an existing game repository is still developed, verified and released
exactly as before, because nothing in those steps requires the new paths.

## Why the Factory release is minor

| Consumer | Reads | After this release |
|---|---|---|
| `wgf_techplan` | `game_design.engine.type`, else the dimension | a declared `phaserjs` is honoured; `dimension: 2d` alone still selects `pixijs`, so every design written before this release plans identically |
| `wgf_init` | `tech_plan.repo_params.game_config.engine` | writes it unchanged; the engine list is now the contract's, not a copy |
| `wgf_develop` | the checkout's `game.config.yaml` | `phaser`/`phaser/*` are the engine's modules for a `phaserjs` game and refused for any other, exactly as `pixi.js` and `three` always were |
| `wgf_sdk`, `wgf_verification`, `wgf_release` | the platform abstraction, the probe, the manifest | untouched: none of them branches on the renderer |
| Existing artifacts | the two schema enums | both only gained a member; nothing that validated before stops validating |

No workflow definition, gate, role, machine, configuration key or platform profile changed.

## What the template release contains

- `packages/phaser-framework/` — `PhaserRenderer` behind the existing `Renderer` seam
  (Phaser 3.90.0). Phaser's `TimeStep` is stopped at boot and the renderer calls
  `game.step(time, delta)` once per drawn frame, so `@wgf/game-core` remains the only loop:
  one `requestAnimationFrame`, one clock, and `Game.pause()` still stops everything during an
  ad break. `destroy()` steps once after `game.destroy(true)` because Phaser defers its
  teardown to the next step, which a stopped TimeStep would never deliver — without that step
  the canvas survives a restart.
- `Renderer.kind` accepts `"phaserjs"`; `createRenderer` has a third branch;
  `src/rendering/phaserjs/` exists alongside the other two.
- **One engine per bundle.** A third dynamic import would have put Phaser's 1.5 MB into every
  build, so the engine is now a build-time constant (`import.meta.env.WGF_ENGINE`, defined by
  the game-config plugin) and Rollup drops the branches a build does not use. Measured: a
  PixiJS build's `dist/` fell from 17 MB to 3.2 MB (it had been carrying the Three.js chunk
  since before this work) and contains no Phaser; a Phaser build contains no PixiJS or
  Three.js.
- `pnpm build:engine <engine.type>` builds the committed config with only `engine.type`
  changed; `verify.yml` runs it for every engine the template implements and re-runs the smoke
  suite against each.
- `tests/e2e/lifecycle.spec.ts`: hidden tab stops the steps and the frames, unhiding resumes
  both.

## What this release does not cover

- **No Phaser golden run.** A golden replays a whole example game the template ships; there is
  no Phaser example, and writing one is a large amount of game content for a renderer the
  pipeline does not branch on. Phaser is proved instead at the template level (build, boot,
  canvas, stepping, pause/resume per engine in CI) and at the Factory module level (plan,
  init, develop conformance). See [golden-runs.md](golden-runs.md).
- **No live agent run** built a Phaser game. The develop brief, the craft playbook and the
  skill are written and tested; no unattended developer has been measured against them.
- **The Phaser Game Agent MCP is not wired.** Its semantics were read from the published skill
  and CLI: it is a managed **cloud sandbox** with its own engine and project layout, browser
  sign-in and credit billing. `seed_game`, `write_files`, `verify` and `preview` act on that
  cloud workspace, not on a template checkout, so they cannot own this repository's files. It
  is recorded in [production-craft-and-mcp.md](production-craft-and-mcp.md) as an opt-in,
  read-only knowledge source (`guide`, `open_project`, `read_files`, `search_games`,
  `search_blocks`), and the develop brief names it that way for a `phaserjs` title.
- **Phaser 4** (4.2.1 is current) is not evaluated. 3.90.0 was chosen for the documented,
  stable `TimeStep.stop()` / `Game.step()` behaviour this integration depends on, and for the
  size of the v3 example corpus a developer will lean on.
- The SDK browser matrix still builds `pixijs` and `threejs` only. The platform abstraction
  does not touch the renderer, and a third engine would multiply an already long matrix.
